# 复盘:烧录后串口消失(2026-10-27 · 电子海洋移植)

## 最终结论

**`nrfutil mcu-manager serial reset` 软复位 = 罪魁祸首。上传本身没有任何问题。**

| 操作 | 次数 | 结果 |
|---|---|---|
| upload + `serial reset`(命令行软复位) | 3 次(0.0.110 / 111 / 112) | 3 次全灭:USB CDC+DFU 一起消失,XIAO 从总线上消失 |
| upload + **手动点按 RST**(物理复位) | 1 次(0.0.112) | 板子正常回来,跑电子海洋,串口恢复 |

机制(推断,Not fully verified):`serial reset` 从 DFU loader 上下文发起软复位,nRF54 的 USB 控制器没有被完整复位、CDC 不重新枚举——这与 41 天前 memory 里记录的现象一致(CPU 在跑、SWD 可读,只是 USB 没起来)。物理 RST 是全芯片上电复位,USB 彻底重来,所以每次都好。
诚实记录一个反例:今天更早一次 `serial reset` 后 wakeword 曾正常起来过一次,所以软复位不是 100% 必死——但 3:1 的复现率足够说明**操作上永远不该再用它**。

`image-list` 显示 slot 1 = "0.0.0, active=true" 两次都被我当成异常线索,事后看是正常布局:板 dtsi 注明旧 bootloader 布局 = mcuboot + slot0 应用 + **slot1 工厂 loader**,"0.0.0" 就是那个 loader。

## 我犯的错误(按严重程度)

1. **用了 `serial reset` 还连用三次。** 最讽刺的是:`8_AI_Wakeword/flash.sh` 和本工程 `flash.sh` 的注释里白纸黑字写着 *"Tap RST to reset the board"*——用户一直靠手动按 RST,从来没问题;我却自作主张用命令行 reset,三次全灭。**证据一直在眼前,没有看。**
2. **归因错误 #1(0.0.111):** 猜测是镜像没自我确认(`boot_write_img_confirmed` 缺失),加上之后照样死 → 假设被证伪。白白烧了一次。
3. **归因错误 #2(0.0.112):** 又把责任推给 LOG/`LOG_MODE_IMMEDIATE` 配置,花 **251 秒**全量重构成 6axis 基准版,烧上去还是死 → 固件配置彻底排除,但又是白白一轮编译+烧录。两次都在"改代码"而不是"做实验"。
4. **对照实验一拖再拖。** 我自己在 0.0.111 失败后就说过"再用 wakeword 已知好镜像做对照实验",结果先去改了代码——如果当时就做实验,一次就能把"我的镜像有问题"和"流程有问题"分开,能省下整整两轮。
5. **把未验证的假设写成了结论。** 在 memory(`nrf54lm20b-flash-serial-disappear.md`)里把 self-confirm 假设写成"强嫌疑根因",违反了本项目"不能把最大概率解释为真实正确率、未验证要标 Not verified"的约束——错误归因如果留着,下次还会误导排查方向。(已修正。)
6. **flash.sh 的验证输出被 `grep | tail -1` 压缩**,烧录是否真成功只看了一行过滤结果,险些变成"用日志片段代替真实验证";端口自动检测 `ls | head -1` 按字母序抓端口,也不可靠。(已修正。)

## 以后的标准烧录流程(替代 `serial reset`)

```bash
# 1. 进 DFU:按住 B0(P0.09)→ 点按 RST → 松开 B0 → /dev/cu.usbmodem1101
#    (1200bps 软触发在本板不可靠,别依赖)
# 2. 上传,必须确认 task_progress 100% + task_end "success":
nrfutil mcu-manager serial image-upload --json \
  --firmware firmware.signed.bin --serial-port /dev/cu.usbmodem1101
# 3. (可选)image-list 查 slot 0 版本/confirmed
# 4. ★ 手动点按一下板子上的 RST 按钮 —— 不要用 `serial reset` ★
#    (备用:拔插 USB 断电重启,同样有效)
```

版本号每次必须递增(否则 mcuboot 按"same version"拒收)。

## 版本台账(本板 slot 0)

| 版本 | 内容 | 结局 |
|---|---|---|
| 0.0.100/101 | wakeword(用户烧录) | 正常运行 |
| 0.0.110 | 海洋初版(LOG 子系统) | upload 成功,`serial reset` 后消失 |
| 0.0.111 | + boot_write_img_confirmed | 同上 → self-confirm 假设**证伪** |
| 0.0.112 | 6axis 基准重写(printk/无 LOG) | `serial reset` 后仍消失;**手动 RST 后正常运行** → 流程问题实锤,固件无问题 |

固件配置逐项排除:LOG 配置 ✗、self-confirm ✗、6axis 基准 ✗(全部烧上去表现一致),真正的变量只有一个——复位方式。

## 附:代码层面"写死项"复盘(2026-10-27 补)

逐文件盘点所有硬编码点,分三类:

### 一、有硬件背书的写死(全部实跑验证,安全)

**app.overlay:**

| 写死项 | 值 | 依据 | 验证状态 |
|---|---|---|---|
| MOSI/SCK 引脚 | P1.0 / P1.1 | 20A 官方 wiki,D0 在 20B 同为 gpio1.0 | ✅ 灯板点亮 |
| SPI 实例 | spi24 | 跟着引脚走(P1.x 归 spi24),20A 同款 | ✅ 跑通 |
| color-mapping | `<1 0 2>`(GBR) | 20A 原版,灯珠字节序 | ✅ 颜色正常 |
| chain-length | 60(=6×10) | 灯板物理事实 | ✅ |
| 8MHz / 0xF8 / 0xC0 / reset-delay | ws2812-spi 驱动标准值 | Zephyr 官方示例同款 | ✅ |

符合项目约束"不硬编码未知引脚"——没有一个是猜的,全部来自 20A 官方 demo 或 20B 板级 dtsi。

**烧录链:** imgtool `--header-size 0x800 --align 16 --slot-size 0x1BE000` 写死且必须精确匹配分区表——依据是 wakeword 已验证命令,安全;但换板/换 bootloader 布局时必须重新核对。

### 二、设计上故意集中的写死(main.c)

- **矩阵五宏**(`COLS/ROWS/MATRIX_SERPENTINE/MATRIX_COL0_DIR/BRIGHTNESS`):全代码唯一的布线配置点,头注释写明"换板只改这五个宏"。蛇形/列方向照搬 20A——口头通过,方向细节未逐项核对(Not verified)。发现镜像/颠倒只动这两个宏。
- **效果参数**(WATER_CENTER 2.0、spring 2.8 / damping 3.0 / jerk 0.10、调色板):20A 原版"调手感"旋钮,不构成风险。
- **LCG 种子 `12345`**:写死反而是优点——每次上电演化可复现,调试友好。
- 小冗余:main.c 运行时设 ODR 104Hz 与 prj.conf `LSM6DSL_ACCEL_ODR=4` 编译期设值重复,二选一即可;留着两处以后"改一处忘一处"会出假 bug。

### 三、流程性写死(唯一会咬人的)

- **`flash.sh` 的 `IMGVER` 每次必须手动递增**——mcuboot 拒收同版本号,忘了改就烧不进/以为烧了其实没换镜像。防御手段:版本台账(本文档上方表格)。

### 结论

排查期间我把第一、二类(有依据、最终证明没问题)的写死项当嫌疑犯改了两轮——其实从 `image-list` 每次显示写入成功那刻起,Flash 里这些值就已在正常工作。真正的凶手(复位指令)从头到尾不在代码里。**写死项的风险分级:签名参数和版本号 > 矩阵布局宏 > 效果参数;而这次故障与三者都无关。**
